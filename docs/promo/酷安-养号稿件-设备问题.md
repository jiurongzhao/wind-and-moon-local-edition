## ⛔ 稿件 1（暂不发）：12GB 内存，swap 里躺着 4.7GB

> **不要发这一篇。**
> 这组数字是我在实际使用中现场测出来的，但**你本人没有确认观察过这个现象**。
> 发出去等于替没经历过的事背书，评论区一追问就穿帮。
> 想启用的话，先在 Termux 里跑一遍下面这条命令，亲眼看过输出再发：
> `grep -E 'MemTotal|MemAvailable|SwapTotal|SwapFree' /proc/meminfo`

**标题**：K70 Pro 的 12GB 内存，我一看 swap 用了 4.7 个 G

**正文**：

```
随手查了下这台 K70 Pro 的内存，结果有点意外。

在 Termux 里跑：
grep -E 'MemTotal|MemAvailable|SwapTotal|SwapFree' /proc/meminfo

出来是这样：

MemTotal       10.91 GB      ← 标称 12GB，可用 10.91
MemAvailable    2.91 GB
SwapTotal      12.00 GB      ← 内存扩展
SwapFree        7.28 GB

也就是说 swap 里已经压了 4.72GB 出去。

SwapTotal 是 12GB 这点也挺有意思——比物理内存还大。

注意我不是说它在疯狂换页，swap 里躺着不等于正在读写。但一台 12GB 的机器，
可用内存只剩 2.9GB、swap 占了快 5 个 G，这个账不太好看。

你们手上的机器 swap 占多少？贴个数看看。
```

**严谨性说明**：数字全部来自本机实测；给了复现命令；主动澄清「swap 有占用 ≠ 正在换页」，避免夸大。

## 稿件 2：前台八核随便用，退到后台就只剩慢核

**标题**：同一台 K70 Pro，前台能跑满 8 个核，切后台速度掉 10 倍

**正文**：

```
Android 会给应用分 cpuset，前台和后台能用的核心不一样。

先看在 Termux 里能直接验证的部分：
cat /proc/self/cgroup        → 3:cpuset:/foreground
grep Cpus_allowed /proc/self/status  → Cpus_allowed_list: 0-7

前台状态下，8 个核全都给你，没问题。

但退到后台就不是这回事了。我在跑本地模型时实测过同一件事：
同一个 0.5B 模型，前台 48 字/秒，App 退到后台只剩 4.7 字/秒——
差了 10 倍量级。不是被冻结这么简单，是直接给你换成了慢核。

所以"切后台继续跑"这种事，在 Android 上不只是会被冻，
就算没冻也会被限核。前台服务 + 唤醒锁能缓解，但根治不了。

有个坑我踩过：想排查的话别只看"进程还活着"，要看 cgroup.freeze 和
/proc/<pid>/stat 的 CPU 时间增量。CPU 时间不动 = 被冻住了。

你们平时遇到过退后台就断的情况吗？
```

**严谨性说明**：`/proc/self/cgroup` + `Cpus_allowed_list: 0-7` 是本机现场验证的；48→4.7 字/秒那组数字来自项目里的实测记录，文里已注明是「跑本地模型时实测」，没有冒充成通用结论。

## 稿件 3：在 K70 Pro 上跑本地大模型，这台手机教我的几件事

**标题**：拿 K70 Pro 跑本地大模型，被这几个坑教做人

**正文**：

```
试着在这台 K70 Pro（骁龙 8 Gen 3）上跑本地大模型，踩的坑比想象中多，
挑几个反直觉的说，都有实测数据。

1）线程数不是越多越好，4 才是甜点

这台是 1+5+2 的簇结构（1×3.30GHz + 5×A720 + 2×A520）。
llama.cpp 是同步并行的——只要有一个慢核参与，每个同步点都得等它。
实测 0.5B：4 线程稳定 42～52 字/秒；按"核数×0.75"取 6 线程，
变成 24～57 字/秒剧烈抖动；8 线程更差，11～35 字/秒。

所以默认值我改成了 min(4, 核数-1)。

2）GPU 加速在这台机器上别想了

Adreno 一开 -ngl 就被系统 SIGKILL，Hexagon 那边缺 QNN 库。
折腾半天，最后老老实实纯 CPU。

3）Flash Attention 和 KV 量化是负优化

0.5B 上基本是噪声，3B 上反而从 11.3 掉到 8.7 字/秒，
预填充从 42 掉到 22 字/秒。默认关掉。

4）"能加载"不等于"能跑"

3B 模型在可用内存 3.4GB 时 mlock 成功、引擎也报就绪，
但生成时 VmSwap 涨到 430MB、loadavg 7.2，十分钟吐不出一个字。
判断标准要看 VmSwap 和 loadavg，不能只看"引擎就绪"。

第 1 条是我觉得最反直觉的——多给线程反而更慢。
你们有试过在这种大小核机器上跑推理吗？
```

**严谨性说明**：四条全部来自项目内的实测记录，数字具体、可复算；第 1 条还给了簇结构（我已在本机核实频率分布）。这条是最有辨识度的原创内容，酷安搞机受众吃这一套。

## 稿件 4：澎湃 OS3 + Android 16 上遇到的零碎坑

**标题**：澎湃 OS3 上几个不太常见但很烦的小坑

**正文**：

```
攒了几个澎湃 OS3 + Android 16 上的零碎问题，都不致命但挺烦，看看有没有同款。

1）麦克风权限选「仅本次允许」，会话过期会直接把进程杀掉

日志里是 Killing <pid>: one-time permission revoked。
它不是收回权限就完了，是把整个进程干掉。后台跑着东西的话一起没。
所以现在我一律选「仅在使用中允许」。

2）用 adb exec-out screencap 截 WebView，出来是全黑

我一度以为应用渲染坏了——截出来只有状态栏，内容全黑。
实际是系统对 WebView 硬件层的截屏限制，改用 DevTools 的
Page.captureScreenshot 拿到的才是真实画面。

3）截图要等滚动停止

否则会抓到 fling 的中间帧，看起来像元素重叠错位。

4）息屏会把无线调试关掉

这个坑让我断了好几次连接。想长时间连着调试，得盯着别让它熄屏。

都是小问题，但排查起来很费时间。你们还遇到过什么类似的？
```

**严谨性说明**：四条均来自项目里的实际排查记录，症状和判据都写清楚了；不含夸大。
